## SSE 断线重连

### 目标

参考 sim-main 的 SSE 流恢复模式，让 `useRunEvents` 在连接断开时自动重连，而不是直接关闭。

### 前端 `useRunEvents.ts` 重写

改动：

- 移除 `onerror` 中的立即 `closeRunEventStream()`
- 浏览器 `EventSource` 会自动重连，`onerror` 中检查 `readyState`：
  - `CONNECTING`：浏览器正在重连，不干预
  - `CLOSED`：浏览器放弃，手动指数退避重连
- 指数退避：1s → 2s → 4s → 8s → 16s（最大 30s），最多 5 次
- 每次成功收到消息时重置重试计数
- 新增 `onReconnecting(attempt)` 回调供 UI 显示重连状态
- `onError` 仅在耗尽重试次数后调用

新增常量：
```typescript
const MAX_RETRIES = 5
const RECONNECT_BASE_MS = 1000
const RECONNECT_MAX_MS = 30000
```

### 后端改动

**`RemoteRun` 新增字段：**

- `_event_seq: int = 0` — 事件序号，每个事件递增
- `_stream_closed: bool = False` — 流是否已关闭（None sentinel 已消费）

**`emit_remote_event` 改动：**

- 每个事件带 `seq` 字段递增序号
- 消息结构新增 `"seq": run._event_seq`

**`stream_run_events` 改动：**

- 流开始时检查 `run._stream_closed` 和终端状态（`finished`/`failed`/`canceled`）
- 若已结束：直接发送 `finished` 事件并关闭流（避免重连客户端永久挂起）
- 消费到 `None` sentinel 时设置 `_stream_closed = True`

### 事件 schema 更新

- `schemas.py`：`RunEvent` 基类新增 `seq: int`
- `app/api/contracts.ts`：`sseEventBaseSchema` 新增 `seq: z.number()`
- `contracts.test.ts`：所有测试数据新增 `seq` 字段

## OpenCAEHub 借鉴分析

### 背景

对 `learning/OpenCAEHub-main` 做了完整源码级探索。

### 项目定位

OpenCAEHub（炎核）是 C++ 桌面 CAE 集成平台，采用"微核心 + 插件"架构：
- 多进程微服务（MessageCenter/ResourcePool/Logic/Scheduler/UI 各自独立 EXE）
- TCP/WebSocket 进程间通信
- pybind11 桥接 C++ ↔ Python
- 文件式求解器集成（求解器作为外部 EXE 启动，PluginConfig.xml 声明式配置）

### 对 SimFEA Studio 的关键借鉴（6 项）

1. **求解器插件配置格式** — `PluginConfig.xml` 定义 exe 路径、输入模板、输出模板、前后命令
2. **文件式求解器执行 + 前后命令链** — PreCommand/PostCommand 链式调用
3. **输出文件通配符收集** — `*.vtu|*.pvd` 模式匹配收集结果
4. **工作目录隔离** — 每次运行独立 `%projectId%/%taskId%/` 目录
5. **三种执行模式** — HasUI（GUI）、无头（脚本）、HttpClient（HTTP 服务）
6. **数据流图模型** — CfDxFlow 任务节点 + 数据链接边（长期参考）

### 不适用部分

C++ 多进程架构、Drogon/WebSocket、pybind11、Minio 对象存储、Qt UI、XML 格式均不适用于 SimFEA Studio 的技术栈。

### 结论

OpenCAEHub 对 SimFEA Studio 的价值集中在**求解器接入层**——当接下来接入 CalculiX/OpenFOAM/Elmer 时，应该用声明式配置（JSON）定义求解器、用通配符收集输出、用前后命令标准化执行流程。

已更新 ARCHITECTURE_ROADMAP 补充完整分析。

## 后台运行清理

### 目标

落实 sim-main 分析中优先级 3 的"后台清理任务"——当 `.simfea/runs` 目录下积累过多老旧运行时自动清理。

### 设计

参考 sim-main `background/cleanup-logs.ts`，但保持 SimFEA Studio 的 Python 后端技术栈。

**配置新增**（`config.py`）：
- `run_retention_days` — 运行保留天数，默认 90 天，环境变量 `SIMFEA_RUN_RETENTION_DAYS`
- `max_runs` — 最大保留运行数，默认 100，环境变量 `SIMFEA_MAX_RUNS`

**新增模块** `simfea_api/cleanup.py`：
- `cleanup_old_runs(settings, *, now=None)` — 扫描 `runs_root` 下所有 `*/meta.json`，按两条规则清理：
  1. 创建时间超过保留天数的运行 → 移除
  2. 如果保留的运行数仍超过上限 → 从最旧的开始移除
- 返回 `{"removed": N, "kept": M}` 摘要
- 创建时间解析优先级：`meta.json` 的 `created_at` 字段 → 运行目录的 mtime

**启动接入**（`main.py`）：
- 在 `start_api_server()` 之前调用 `cleanup_old_runs()`
- 仅在有移除时记录日志，异常不阻塞启动

| `test_no_runs_found` | 目录存在但无 meta.json → 返回空 |

## 本地 CalculiX 端到端实测与修复（真实 FRD 格式踩坑全记录）

### 背景

上面三个阶段的代码（FRD→VTK 转换器、本地执行引擎、SolverDefinition 增强）合并后，
本地 CalculiX 运行首次实测失败。以下是三次迭代调试的完整记录。

配置环境：
- Windows 11，CalculiX v2.10 bConverged 版本
- 安装路径：`CalculiX_2_10_win_002\bConverged\CalculiX\bin\`
- 关键发现：`ccx.exe` 不能直接执行，必须通过 `ccx.bat` 启动（bat 脚本设置 OMP_NUM_THREADS、PATH 含 DLL 目录）

---

### 第一轮：exit_code=1 — 命令分发错误

**现象**：触发本地运行后 `status=failed, exit_code=1`，stderr 空。

**排查**：检查 `execute_local_run()` 收到的 `run.command` 字段，发现它是：

```bash
bash -lc 'export PATH=...; ...; ccx cantilever; ...'
```

这是因为 `start_solver_run()` 在分发之前无条件调用了 `build_solver_run_script()`
（SSH 远程执行的 bash 脚本），并对本地节点也设置了 `run.command`。

**修复**（`main.py` — `start_solver_run`）：

```python
# 修复前：远程脚本无条件覆盖 run.command
run.command = f"bash -lc {sh_quote(build_solver_run_script(run, solver))}"

# 修复后：仅远程路径设置 command
if is_local_node(node):
    asyncio.create_task(execute_local_run(run, solver))
else:
    run.command = f"bash -lc {sh_quote(build_solver_run_script(run, solver))}"
    asyncio.create_task(execute_remote_run(run, node))
```

同样修复了 `start_demo_run` 中的相同问题。

---

### 第二轮：exit_code=127 — bash 破坏 Windows 路径

**现象**：修复分发后，exit_code 从 1 变为 127（"command not found"）。

**排查**：

1. `_run_local_command()` 的实现使用 `_find_local_shell()` 检测可用 shell。
   Windows 上 Git/MSYS2 提供了 `bash.exe`，被检测到 → 所有命令通过 `bash -lc` 包装执行。
2. bash 将 Windows 反斜杠路径 `H:\dev\...\ccx.bat cantilever` 解释为转义序列
   → `\d`、`\c` 等被消费为无意义的转义字符 → 路径被破坏。
3. 即使路径正确，bash 也无法直接执行 `.bat` 文件（Windows 批处理）。

**修复 1**（`main.py` — `_run_local_command` 重写）：

彻底去掉 bash 检测，始终使用平台原生 shell：

```python
# 修复前：检测 bash 并用 bash -lc 包装
async def _run_local_command(cmd, cwd):
    shell = _find_local_shell()
    with tempfile.NamedTemporaryFile(...) as f:
        f.write(cmd.encode())
        proc = await asyncio.create_subprocess_exec(
            shell, "-lc", f"bash {f.name}", cwd=str(cwd), ...
        )

# 修复后：始终用 create_subprocess_shell（Windows 上为 cmd.exe）
async def _run_local_command(cmd: str, cwd: Path):
    proc = await asyncio.create_subprocess_shell(
        cmd, cwd=str(cwd),
        stdout=asyncio.subprocess.PIPE, stderr=asyncio.subprocess.PIPE,
    )
    stdout, stderr = await proc.communicate()
    return proc.returncode, stdout, stderr
```

`create_subprocess_shell` 在 Windows 上使用 `cmd.exe /c`，正确处理反斜杠路径和 `.bat` 文件。

**修复 2**（`.simfea/config.json`）：

将 `executable` 从 `ccx.exe` 改为 `ccx.bat`：

```json
"executable": "H:\\dev\\projects\\simFEAstudio\\SimFEA-Studio\\CalculiX_2_10_win_002\\bConverged\\CalculiX\\bin\\ccx.bat",
"command_template": "H:\\dev\\projects\\simFEAstudio\\SimFEA-Studio\\CalculiX_2_10_win_002\\bConverged\\CalculiX\\bin\\ccx.bat cantilever"
```

原因：`ccx.bat` 内部设置 `OMP_NUM_THREADS`、将 DLL 目录加入 `PATH`，然后才启动 `ccx.exe`。
直接运行 `ccx.exe` 缺少这些环境准备而失败。

### 第三轮：FRD 解析器对真实 CalculiX 输出全部失效

**现象**：ccx 正常执行（`.dat`/`.frd`/`.sta` 均生成），但 FRD→VTK 转换失败
——`_parse_frd_sections()` 返回空的 `2D`/`2S` 区段，VTK 输出无位移/应力数据。

**根本原因**：`frd_to_vtk.py` 的 FRD 解析器基于互联网文档中描述的遗留格式（`2D`/`2S`
区段头），但 CalculiX v2.10 实际输出使用 `1PSTEP` 结构。

**真实 CalculiX FRD 格式（v2.10）**：

```
    1C                              ← 文件级元数据头
    1UUSER                          ← 用户/日期/程序信息
    1UPGM               CalculiX
    2C                             8                                     1
 -1         1 0.000000E+00 ...      ← 节点坐标（格式 -1）
...
 -3                                 ← 区段终止符
    3C                             1                                     1
 -2         1         2  ...        ← 单元连接（格式 -2 = 8 节点六面体）
 -3
    1PSTEP                         1           1           1   ← Step 结果
  100CL  101 ...                    ← 类头（跳过）
 -4  DISP        3    1             ← 数据类型描述符：位移，3 分量
 -5  D1          1    2    1    0   ← 分量描述符（跳过）
 -5  D2          1    2    2    0
 -5  D3          1    2    3    0
 -1         1 0.000000E+00 ...      ← 该节点的位移数据
...
 -3
    1PSTEP                         2           1           1   ← 下一 Step
  100CL  101 ...
 -4  STRESS      6    1             ← 数据类型描述符：应力，6 分量
 -5  SXX         1    4    1    1
...
 -1         1 0.000000E+00 ...      ← 该节点的应力数据
...
 -3
  9999                              ← 文件结束
```

关键差异：

| 方面 | 遗留格式（文档描述） | 真实格式（v2.10） |
|------|---------------------|-------------------|
| 位移数据 | `2D` 区段头 | `1PSTEP` 内 `-4 DISP` 描述符 |
| 应力数据 | `2S` 区段头 | `1PSTEP` 内 `-4 STRESS` 描述符 |
| 区段终止 | 下一个区段头 | `-3` 显式终止符 |
| 区段头格式 | 裸键（`2C`） | 带尾随数据（`    2C                             8                                     1`） |
| 元数据 | 无 | `1C`/`1U` 文件头行 |
| 分量定义 | N/A | `-5` 分量描述符行 |

**`_parse_frd_sections()` 完全重写**（`frd_to_vtk.py`）：

```python
def _parse_frd_sections(text: str) -> dict[str, list[list[float]]]:
    sections: dict[str, list[list[float]]] = {}
    current_key: str | None = None
    data_section_codes = {"2C", "3C"}

    for line in text.splitlines():
        stripped = line.strip()
        if not stripped:
            continue
        if stripped == "-3":
            current_key = None          # 区段终止
            continue
        if stripped == "9999":
            continue                     # 文件结束
        code = stripped[:2]

        # 几何区段（2C = 坐标, 3C = 单元）
        if code in data_section_codes:
            current_key = code
            sections.setdefault(current_key, [])
            continue

        # 1PSTEP: Step 结果开始 → 重置状态，等待 -4 描述符
        if code == "1P":
            current_key = None
            continue

        # 100CL: Step 内类头行 → 跳过
        if code == "10":
            continue

        # -4: 数据类型描述符（DISP → "2D", STRESS → "2S"）
        if code == "-4":
            upper = stripped.upper()
            if "DISP" in upper:
                current_key = "2D"
                sections.setdefault("2D", [])
            elif "STR" in upper:
                current_key = "2S"
                sections.setdefault("2S", [])
            continue

        # -5: 分量描述符 → 跳过
        if code == "-5":
            continue

        # 1C/1U: 文件头元数据 → 不在任何区段内
        if code in ("1C", "1U"):
            current_key = None
            continue

        if not current_key:
            continue

        values = _parse_frd_line(line)
        if values:
            sections[current_key].append(values)

    return sections
```

关键设计决策：
- 区段头改用 `startswith` 匹配（`stripped[:2]`），而非精确匹配，因为真实区段头带尾随元数据
- 位移/应力数据从 `-4` 描述符推断类型，映射到内部键 `"2D"`/`"2S"` 以保持下游兼容
- 严格的状态机：`-3` 终止任何活跃区段，`1PSTEP` 重置结果键
- `-5` 分量描述符和 `100CL` 类头均跳过，仅提取 `-1` 数值数据行

**`_parse_elements()` 修复 — 跳过一维梁扩展数据**：

真实 3C 区段包含两类行：
- `-1` 格式：一维梁单元扩展信息（`[format, elem_id, n1, n2]`）——用于 B31 梁
- `-2` 格式：三维实体单元（`[format, n1..n8]`）——用于 8 节点六面体

原代码不区分格式号，导致 `-1` 行被错误解析为单元（node 0 被包含在连接中）。
修复：跳过 `-1` 行，仅使用 `-2` 行。

```python
def _parse_elements(elem_rows):
    elements = []
    for row in elem_rows:
        if len(row) < 3:
            continue
        fmt = int(row[0])
        if fmt == -1:
            continue        # 跳过一维梁扩展数据，不用于三维可视化
        if fmt == -2:
            elements.append([int(n) for n in row[1:]])  # 8 节点六面体
    return elements
```

**`frd_to_vtk()` — 结果数据解析适配**：

位移和应力数据不再来自独立的 `2D`/`2S` 区段，而是在 `1PSTEP` 内通过 `-4` 描述符
定向提取后存入同名键。`_parse_nodal_data()` 保持不变（按 `[format, node_id, v1..vn]`
结构解析）。

---

### 输入文件格式修复

在 FRD 解析修复的同时，发现三个 CalculiX 输入文件问题：

**1. `*CLOAD` 位置错误**

`*CLOAD` 必须在 `*STEP` 内部。原输入文件将其放在 `*STEP` 之前，CalculiX 报错。
修复：移动到 `*STATIC` 之后。

```
# 修复前（错误）
*STEP
*STATIC
*END STEP
*CLOAD           ← 在 STEP 外部，CalculiX 报错

# 修复后（正确）
*STEP
*STATIC
*CLOAD           ← 在 STEP 内部
2, 2, -100.
*NODE FILE
U
*EL FILE, ELSET=beam
S
*END STEP
```

**2. `*NODE PRINT` → `*NODE FILE`**

`*NODE PRINT` 输出到 `.dat` 文本文件，`*NODE FILE` 输出到 `.frd` 二进制结果文件。
FRD→VTK 转换需要 `.frd` 中的结果数据，因此必须使用 `*NODE FILE` / `*EL FILE`。

**3. 单位制一致性**

原输入文件混用 m 和 MPa（210e9 弹性模量，1m 单元长度），与 CalculiX 的
N-mm-MPa 一致单位制不匹配，导致 8933mm 的不合理位移。修复为：
- 节点坐标：`0, 0, 0` 和 `1000, 0, 0`（mm）
- 弹性模量：`210000`（MPa）
- 截面尺寸：`20, 20`（mm）
- 载荷：`-100`（N）

修复后位移 8.93mm，符合理论值。

### 求解器配置合并修复

**问题**：用户 `.simfea/config.json` 中仅配置了 `calculix` 求解器，
但 `load_settings()` 用用户配置**替换**了全部默认求解器列表，
导致 `openfoam` 和 `elmer` 求解器定义丢失。

**修复**（`config.py` — `load_settings()`）：

```python
# 按 alias 合并：默认求解器提供基础（含 input_files 模板），
# 用户配置的同名求解器覆盖个别字段
default_solver_items = {s["alias"]: s for s in default_config().get("solvers", [])}
raw_config.setdefault("solvers", [])
for item in raw_config["solvers"]:
    alias = item["alias"]
    if alias in default_solver_items:
        merged = dict(default_solver_items[alias])
        merged.update(item)
        default_solver_items[alias] = merged
    else:
        default_solver_items[alias] = item
raw_config["solvers"] = list(default_solver_items.values())
```

这样用户只需覆盖 calculix 的 `executable` 和 `command_template`，
openfoam/elmer 的默认定义保持不变。
